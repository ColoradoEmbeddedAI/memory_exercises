# distillation_lab — Activity companion (PyTorch KD experiments + optional ExecuTorch/CMSIS-NN firmware)

Companion project for
[`../lecture7-activity-knowledge-distallation-handout.md`](../lecture7-activity-knowledge-distallation-handout.md),
which walks through every part. The activity is optional and self-paced.

It trains a 784-30-10 MLP student on MNIST, with and without a LeNet-300-100 teacher, and measures:

- **Parts 0–4 (laptop):** what soft targets look like, how T, α and the T² factor matter with plenty of labels and with few, how far 1,000 labels plus 54,000 unlabeled images get, and whether a student can learn a digit it never saw
- **Part 5 (laptop, optional board):** whether the teacher and the student fit the STM32F407, and, on the board, that distillation changes accuracy and nothing else
- **Part 6 (laptop, extension):** KD as the recovery step after structured pruning, on the pruning lab's Model B2 and Fashion-MNIST

Every training run takes a few seconds, so each configuration runs with 3 seeds.

## Prerequisites

- **Parts 0–6:** the ExecuTorch venv from earlier labs (`~/executorch/et-env`), which has PyTorch. Nothing else; there's no torchvision dependency.
- **Part 5's board step:** everything from the quantization lab: `arm-none-eabi-gcc` 13.x, OpenOCD, CMake, Ninja, a 3.3 V USB-UART adapter on PA2, and its ExecuTorch tree with the Cortex-M backend and CMSIS-NN at `~/executorch/executorch-build/cortex-m4-cmsis`, plus the CMSIS-NN checkout at `~/executorch/CMSIS-NN`. Follow "Prerequisites" in [`../../06_quantization/quantization_lab/README.md`](../../06_quantization/quantization_lab/README.md). `cmake --preset stm32` checks for the tree and the portable ops this lab needs (`aten::addmm`, `aten::permute_copy`, `aten::relu`, `dim_order_ops::_clone_dim_order`).

## Running it

```bash
source ~/executorch/et-env/bin/activate
cd distillation_lab
python3 python/data.py                  # download MNIST, print the splits

python3 python/part0_warmup.py          # ~10 s
python3 python/part1_baseline_vs_kd.py  # ~30 s
python3 python/part2_sweeps.py          # ~8 min (--regime full or 1k: ~4 min each)
python3 python/part3_low_data.py        # ~1 min; needed before Part 5's board step
python3 python/part4_missing_digit.py   # ~30 s
python3 python/part5_fit.py             # instant
python3 python/part6_pipeline.py        # ~7 min; --long adds ~13 min
```

The times are for a 12-core laptop CPU with 4 PyTorch threads per script (`KD_THREADS`, default 4). The MLP is small enough that more threads don't help much; running two scripts at once does.

Board (optional), after Part 3:

```bash
scripts/run_board.sh teacher int8       # under 10 s each; UART=/dev/ttyUSBn for another adapter
scripts/run_board.sh 3c int8
scripts/run_board.sh 3a int8
scripts/run_board.sh 3c fp32
scripts/run_board.sh teacher fp32       # fails to link, on purpose (handout Part 5, Step 3)
python3 python/part5_fit.py             # now includes the board's numbers
```

By hand (or on macOS, where `stty -F` differs):

```bash
python3 python/export_mlp.py --model 3c --precision int8
cmake --preset stm32 && cmake --build --preset stm32 --target flash
picocom -b 115200 --imap lfcrlf /dev/ttyUSB0      # reset the board; save the output to results/3c-int8.txt
```

## Implementation notes

- **No DataLoader.** All of MNIST is held as float32 tensors (about 200 MB) and `train()` slices batches from a reshuffled permutation. For a 24K-parameter model, a DataLoader's per-batch overhead would cost more than the training itself. A run of 4,300 steps takes about 3 s without a teacher and 6 s with one.
- **Fixed steps, not epochs.** `train()` counts optimizer steps and cycles through the data as often as needed. Part 3 depends on this: 4,300 steps is 10 passes over `train_full` but 550 over `labeled_1k`.
- **Part 3c's mixed batches.** `labeled_1k` and `unlabeled_rest` are concatenated, and batches are drawn uniformly from all 55,000 images, so labeled images appear in proportion to their number (about 2 per batch). Unlabeled images have label −1, and `kd_loss()` gives them the soft term only (α = 1 for that image). On a fully labeled batch, `kd_loss()` equals `kd_loss_slide()`; Part 0 prints both.
- **The teacher.** LeNet-300-100 with dropout 0.2, trained with the same recipe for 20 epochs (`train_teacher.py`, seed 0). It reaches 98.05% test accuracy. As the handout's Part 0 shows, it is very confident at T = 1, which is typical of a well-trained MNIST model and is exactly what temperature is for.
- **Seeds.** A seed sets the student's initialization and the batch order. In Part 6 the student starts from the slimmed variant A, so there the seed sets only the batch order, and the seed-to-seed spread is correspondingly tiny.
- **Part 6's slimming** is the pruning lab's `make_C()` without its fine-tune: keep the 8 conv1 and 16 conv2 filters with the largest L1 norm, and copy them and the matching input slices into a `ModelB2(8, 16)`. `fashion_b2.py` has Model B2 in the pruning lab's order (pool before ReLU), and the pruning lab's train/val split.

## Firmware notes

The firmware is the quantization lab's, with three changes: the input shape comes from the program (1×784 here) instead of being fixed at 1×1×32×32; the test images are 784-byte MNIST digits; and its avgpool fix is gone (an MLP has no pooling). It compiles CMSIS-NN from source with unaligned access allowed, as the quantization lab does; see that lab's README for why.

- **int8 builds** quantize the float input with their first op and dequantize the logits with their last. Each Linear, with its ReLU fused, is one `cortex_m::quantized_linear` (CMSIS-NN). The teacher's two `dim_order_ops::_clone_dim_order` instructions are copies that the export leaves between layers; together they take under 5,000 of the teacher's 838,000 cycles.
- **fp32 builds** run portable kernels: `aten::permute_copy` transposes each weight matrix into the planned arena on every inference, then `aten::addmm` multiplies. That's why the fp32 student's arena (97,344 B) is nearly the size of its fc1 weights, and why the fp32 teacher would need 945,136 B of SRAM if its 1,069,768-byte `.pte` fit in Flash. It doesn't: the link fails with "region `FLASH' overflowed by 406060 bytes".
- **The 200 test images** are stored as uint8 (157 KB) and converted with the same 256-entry lookup table that `data.py` uses, so the board's inputs are bit-for-bit the laptop's.

## Board memory budget

| Region | Holds | Size |
|---|---|---:|
| Flash | runtime, portable and CMSIS-NN kernels, about 225 KB; the `.pte`, 27–273 KB (int8) or 98 KB (fp32 student); 200 test images, 157 KB | 410–657 KB of 1 MB |
| Main SRAM | `planned_pool`, 112 KB; the rest of `.data`/`.bss`, about 3.9 KB; stack, the rest (about 12 KB) | 128 KB |
| CCM | `method_pool` 16 KB (1.0–2.2 KB used); `temp_pool` 8 KB (under 200 B used); input staging buffer 3 KB | 27 KB of 64 KB |

`planned_pool` is sized for the largest build that fits (the fp32 student, 97,344 B), so `arm-none-eabi-size` reports the same SRAM for every build; the `Planned arena` line on the UART is the number that changes.
